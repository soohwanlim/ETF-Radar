# ETF Radar 남은 작업 로드맵

이 문서는 현재 구현 상태를 기준으로 **아직 남은 작업만** 관리한다. 이미 제공 중인 기능은 재구현하지 않고, 기능을 확장할 때도 기존 정적 데이터 파이프라인과 화면을 우선 재사용한다.

## 작업 시작 원칙

1. 작업 시작 직전에 원격 `main`을 갱신하고 그 커밋에서 작업 브랜치를 만든다.

   ```bash
   git fetch origin main
   git switch main
   git pull --ff-only origin main
   git switch -c <type>/<short-description>
   ```

2. `README.md`, 이 문서, 관련 화면과 수집 스크립트, 최근 커밋을 확인해 같은 기능이 이미 있는지 먼저 조사한다.
3. 기존 기능을 복제하지 않는다. 겹치는 요구사항은 기존 컴포넌트·데이터·스크립트를 확장한다.
4. 한 PR은 한 가지 사용자 문제만 해결하고, 데이터 형식 변경은 수집기·화면·테스트·문서를 함께 갱신한다.
5. 구현 전후에 `npm test`, `npm run lint`, `npm run build`를 실행한다.

## 현재 완료된 범위

다음 항목은 이미 구현되어 있으므로 신규 과제로 다시 만들지 않는다.

- 국내 주식형 현물 ETF 수익률 랭킹과 기간별 수익률
- ETF 상세, 가격 차트, TOP 10 구성자산 및 변경 내역
- 테마별 탐색, 액티브 ETF 분석, ETF 비교, 즐겨찾기
- 구성종목 변경 감지와 종목별 상세 화면
- 가이드, 방법론, FAQ, 문의, 정책, 인사이트 콘텐츠
- KRX/Naver 기반 정적 데이터 수집, OHLC 누적, 데이터 상태 표시
- 예약 수집, 배포 데이터 헬스체크, 실패 Issue 생성
- 정적 프리렌더링, 동적 ETF 메타데이터, sitemap 생성

## 우선순위

### P0 — 데이터 신뢰성과 장애 대응

#### 1. 데이터 계약 검증 강화

- `etfs.json`, holdings, changes, OHLC manifest 사이의 코드·기준일 정합성을 자동 검증한다.
- 중복 ETF, 미래 기준일, 비정상 수익률, 음수 가격·순자산, OHLC 역전 등 오류 조건을 명시한다.
- 수집 전후 검증 실패 시 잘못된 정적 데이터가 커밋되지 않도록 한다.
- **완료 기준:** 정상 fixture와 주요 실패 fixture가 있고 CI에서 회귀 테스트가 실행된다.

#### 2. 수집 결과 관측성 개선

- 성공·부분 성공·실패 원인을 데이터 소스와 단계별로 구분한다.
- Actions summary와 실패 Issue에 실패 ETF 수, 최근 정상 기준일, 실패 단계, 재실행 판단 정보를 싣는다.
- 동일 원인의 반복 Issue는 하나로 묶고 정상화 시 닫는 절차를 문서화한다.
- **완료 기준:** 운영자가 Issue와 summary만 보고 데이터 지연, 외부 소스 장애, 코드 오류를 구분할 수 있다.

#### 3. 거래일 판정 회귀 테스트

- 주말, 법정 공휴일, 임시 휴장일, 연말 폐장일, 다음 해 첫 거래일 fixture를 추가한다.
- KRX 공개 지연과 실제 휴장을 구분하는 헬스체크 시나리오를 검증한다.
- **완료 기준:** 시장 달력 변경 시 갱신 위치와 검증 절차가 문서화되고 자동 테스트가 통과한다.

### P1 — 데이터 범위와 분석 품질

#### 4. 전체 구성종목 수집 어댑터

- 현재 TOP 10 범위를 유지하면서 운용사별 공식 PDF/CSV 제공 여부와 이용 조건을 먼저 조사한다.
- 공통 holdings 스키마, 출처, 공시 기준일, 수집 실패 시 fallback 규칙을 정의한다.
- 지원 범위가 가장 넓고 형식이 안정적인 운용사부터 어댑터를 단계적으로 추가한다.
- 화면에서는 TOP 10과 전체 포트폴리오를 명확히 구분한다.
- **완료 기준:** 최소 1개 운용사의 전체 구성종목을 출처·기준일과 함께 제공하고 기존 TOP 10 동작에 회귀가 없다.

#### 5. 변경 신호 품질 지표

- 단순 진입·이탈 외에 데이터 연속성, 변경 지속 기간, 여러 ETF의 동시 변화 여부를 표시한다.
- 설정·환매나 가격 변화가 구성수량 변화로 오해되지 않도록 방법론과 화면 설명을 함께 보강한다.
- **완료 기준:** 모든 신호에 산출 근거, 데이터 한계, 충분한 데이터가 없을 때의 상태가 표시된다.

#### 6. 비교 기능 확장

- 기존 비교 화면에 비용, 순자산, 거래량, 구성종목 중복도 등 의사결정에 필요한 지표를 단계적으로 추가한다.
- 지표별 기준일과 결측값을 명확히 표시하고, 동일 기준이 아닌 값은 직접 비교하지 않는다.
- **완료 기준:** 공유 가능한 비교 상태 또는 URL과 모바일 접근성 검증을 제공한다.

### P2 — 성능, 접근성, 검색 품질

#### 7. 성능 예산과 자동 측정

- 기존 Lighthouse 기준점을 바탕으로 홈, 변경 감지, ETF 상세를 우선 최적화한다.
- 큰 JSON을 용도별로 분리하거나 필요한 필드만 내려받고 초기 렌더링 작업량을 줄인다.
- 주요 페이지의 번들 크기와 Lighthouse 회귀를 정기적으로 기록한다.
- **완료 기준:** 모바일 목표 점수(Performance 85+, 나머지 90+)를 충족하거나 예외 사유와 후속 작업이 기록된다.

#### 8. 접근성 회귀 점검

- 키보드 탐색, 포커스 표시, 표·차트 대체 설명, 색상 외 등락 표현, heading 순서를 점검한다.
- 주요 사용자 흐름을 axe 또는 동등한 자동 검사와 수동 키보드 테스트로 확인한다.
- **완료 기준:** 홈→상세→비교의 핵심 흐름에 치명적 접근성 오류가 없다.

#### 9. 색인 및 콘텐츠 품질 모니터링

- Search Console에서 sitemap 처리, 제외된 ETF 상세 페이지, canonical 오류를 정기 확인한다.
- 얇은 상세 페이지는 억지로 색인하지 않고 현재 품질 기준을 유지·조정한다.
- **완료 기준:** 월별 점검 기록에 색인 수, 제외 원인, 수정 여부가 남는다.

### P3 — 운영과 사용자 피드백

#### 10. 피드백 처리 흐름

- 오류 제보에 ETF 코드, 기준일, 화면 URL, 기대값을 포함하도록 문의 경로를 구조화한다.
- 데이터 오류와 기능 제안을 분류하고 우선순위 판단 기준을 정한다.
- **완료 기준:** 접수부터 재현, 수정, 사용자 고지까지의 담당 절차가 문서화된다.

#### 11. 개인정보·광고 정책 최종 점검

- 분석 도구 또는 광고 도입 전에 실제 수집 항목, 쿠키, 보존 기간, 제3자 제공 내용을 정책에 반영한다.
- 도입하지 않은 추적 기능을 정책에 미리 기재하지 않는다.
- **완료 기준:** 배포 설정과 정책 문구가 일치하고 모바일에서 고지·동의 흐름을 확인한다.

## 보류 항목

다음 항목은 서비스의 정적·종가 기반 원칙을 바꾸므로 별도 의사결정 없이 착수하지 않는다.

- 실시간 시세, 주문 또는 투자 추천 기능
- 로그인, 서버 DB, 사용자 간 포트폴리오 공유
- 해외 ETF·채권·원자재 등 현재 수집 범위 밖의 자산
- 근거 데이터를 설명할 수 없는 AI 매수·매도 점수

## 권장 실행 순서

1. 데이터 계약 검증 강화
2. 수집 관측성과 거래일 테스트
3. 전체 구성종목 어댑터 사전 조사 및 1개 운용사 시범 적용
4. 변경 신호와 비교 지표 개선
5. 성능·접근성·검색 품질 자동 점검
6. 사용자 피드백과 정책 운영 정비

새 작업을 추가할 때는 기존 완료 범위와 중복되지 않는지 확인하고, 우선순위·사용자 가치·완료 기준을 반드시 함께 기록한다.
